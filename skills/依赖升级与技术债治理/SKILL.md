# 依赖升级与技术债治理

## 使命

按安全、兼容性和维护收益管理依赖变更与技术债偿还。 本技能是纯指导型工作框架：Trae 应读取项目事实、现有约束和可用工具后自主选择分析方法、参数、工具与执行顺序，而不是机械套用固定命令。

## 适用情形

当任务涉及依赖盘点、漏洞与许可、兼容影响、升级批次、验证回退、债务排序时启用。若请求主要属于其他专业技能，应说明边界并转交，不重复制造相互冲突的结论。

## 工作原则

- 升级决策基于证据而非新鲜度：每个依赖变更必须评估安全修复、兼容性影响、维护状态和迁移成本后才执行。
- 技术债量化：每次识别技术债必须标注影响范围、发生频率、恶化速度和偿还成本，不能仅凭主观感受。
- 锁定与可复现：依赖版本必须锁定到精确版本（含传递依赖）；构建必须可复现，不依赖浮动版本或外部网络。
- 渐进偿还：技术债按风险和价值排序偿还，优先处理安全漏洞和导致生产事故的债项；新功能不堆积新债。

## 工作流程

### 1. 审计依赖清单

扫描直接和传递依赖，提取当前版本、最新版本、已知漏洞（CVE）、许可变更和弃用声明。

### 2. 评估变更影响与风险

对每个可升级依赖评估：变更日志、API 破坏、性能影响、传递依赖变化、回滚成本。

### 3. 制定升级与技术债偿还计划

区分安全升级（立即）、兼容升级（本迭代）、破坏性升级（计划窗口）和技术债偿还（按严重度排期）。

### 4. 执行升级

逐个依赖进行升级，每次变更后运行完整测试套件；失败时回滚并记录原因。

### 5. 锁定与记录

将精确版本写入锁定文件，更新变更日志和技术债台账。
## 用户确认边界

遇到关键需求歧义、不可逆或破坏性操作、生产环境写入、敏感权限或秘密、外部发布、费用承诺、法律与业务风险取舍时，必须暂停并请求用户或责任人明确确认。普通的只读检查、可逆分析和已授权范围内的实现由 Trae 自主推进，避免对每个细节反复询问。

## 专项边界

不为追求最新而升级，不混入无关重构，不忽略锁文件、传递依赖和回退路径。

## 路由与协作

可将专项工作转交给：安全审查与威胁建模、测试策略与质量保障、CI-CD与发布管理、代码设计。默认将上述技能作为专项协作方，当前主技能保留目标、进度和最终验收责任。只有当前技能已不再适合承担主目标时才切换主技能；切换或协作时提供上下文、已验证事实、未决问题、风险等级、期望输出和返回条件。协作结果返回当前主技能验收；没有新增证据或状态变化时不得重复转交。

## 状态模型

每项工作只能以以下状态之一汇报：已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证。状态后必须附证据或阻塞原因；“已完成”要求验收条件已经被验证，“无法验证”必须说明所缺环境、权限或数据。

## 完成标准

- 范围、假设、事实和决策边界清楚。
- 高风险事项有处置、接受、转交或明确阻塞结论。
- 关键结论具备可复核证据，验证与回退方式匹配风险。
- 未决事项具有负责人、触发条件或下一步，不用模糊措辞掩盖不确定性。
- 每一项未升级的已知漏洞已评估风险并记录了接受的残余风险或阻塞原因。
- 技术债台账已更新：每项债的偿还成本和阻塞影响已量化。
