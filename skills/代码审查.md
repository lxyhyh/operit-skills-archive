# 代码审查

## 使命

基于正确性、风险和可维护性提供有证据、可执行且分级的审查反馈。 本技能是纯指导型工作框架：Trae 应读取项目事实、现有约束和可用工具后自主选择分析方法、参数、工具与执行顺序，而不是机械套用固定命令。

## 适用情形

当任务涉及行为正确性、安全、测试、接口、复杂度、兼容性、审查结论时启用。若请求主要属于其他专业技能，应说明边界并转交，不重复制造相互冲突的结论。

## 工作原则

- 审查以证据说话：每个审查意见必须有具体位置（文件+行号）、证据和影响说明；没有证据的"感觉不好"不构成审查意见。
- 分级反馈：区分 Blocker（必须修复）、重要建议（应修复）和非阻塞建议（可自行决定），不把 Nit 上报为 Blocker。
- 审查变更的上下文：不只看 diff 行，必须理解变更在完整文件中的行为影响；差分行不是独立存在的。
- 作者拥有修复：审查者指出问题和修复方向，但不直接重写代码；代码所有权和责任属于作者。

## 工作流程

### 1. 理解变更意图

阅读 PR 描述、关联 Issue 和设计文档；理解"为什么改"比"改了什么"更重要。

### 2. 逐层审查

按接口契约→数据状态→并发安全→错误处理→安全→性能的顺序逐层检查。

### 3. 运行验证

拉取代码本地构建和运行测试；对新行为手动验证关键路径和边界。

### 4. 输出审查结论

每个问题标注严重度、位置、证据和修复建议；汇总给出通过/有条件通过/拒绝的审查结论。

### 5. 复核修复

作者修复后重新审查相关部分，确认问题已解决且无新问题引入。
## 用户确认边界

遇到关键需求歧义、不可逆或破坏性操作、生产环境写入、敏感权限或秘密、外部发布、费用承诺、法律与业务风险取舍时，必须暂停并请求用户或责任人明确确认。普通的只读检查、可逆分析和已授权范围内的实现由 Trae 自主推进，避免对每个细节反复询问。

## 专项边界

不把个人风格包装成缺陷；区分阻塞项、重要建议和非阻塞建议。

## 领域深化

### 分层审查清单

审查不同层面时优先关注该层面的专属问题，不混用标准：

**接口/契约层**
- 函数签名变更是否向后兼容（新增可选参数 = 兼容；删除/重命名/改变必需参数 = 不兼容）。
- 公开 API 的错误语义是否一致（同类错误返回相同状态码和错误格式）。
- 是否有未文档化的副作用（修改全局状态、隐式数据库写入、外部服务调用）。

**数据与状态层**
- 是否存在非原子的读-改-写序列（TOCTOU 竞态）。
- 事务边界是否覆盖所有必须一致的操作；回滚是否会留下不一致状态。
- 缓存失效策略是否与数据写入同步——是否存在读到过期数据的窗口。

**并发与线程安全**
- 共享可变状态的访问是否受适当同步保护（锁、通道、原子操作）。
- 是否存在死锁可能（多锁获取顺序不一致、持有锁时调用外部代码）。
- 异步操作的生命周期是否正确管理（取消/超时时不泄漏资源或留下悬挂回调）。

**错误处理与韧性**
- 是否吞掉异常而无日志或无降级逻辑（空 catch 块）。
- 重试逻辑是否有退避、最大次数和可重试错误的明确范围。
- 外部调用是否有超时设置；超时后是否正确回收资源。

**安全**
- 用户输入是否在正确的上下文中转义/参数化（SQL = 参数化查询，HTML = 实体编码，系统命令 = 禁用或严格白名单）。
- 敏感数据是否在日志、错误消息、调试输出中泄漏。
- 授权检查是否在操作前执行且无法绕过（不依赖前端隐藏）。

### 常见反模式

- **审查变成重写**：替代式建议而非指出问题+修复方向，剥夺作者的修复所有权。
- **无证据断言**："这样写不安全"但未引用行号、未提供攻击链或违反的标准。
- **严重度膨胀/压缩**：将 Nit 上报为 Blocker（浪费作者时间）或将数据丢失风险标记为 Medium（掩盖风险）。
- **只审查新增代码**：变更可能使已有代码进入不可达状态或产生非预期交互，差分行不代表完整上下文。
- **忽视测试代码**：测试代码中的缺陷会制造虚假安全感或 flaky tests。

### 领域门禁

在交付审查结论前必须确认：
- 每个问题的位置（文件+行号）、证据、触发条件和影响均已提供。
- 严重度标记与修复时效匹配（Blocker → 立即；High → 本迭代；Medium → 本/下迭代；Low/Nit → 可推迟）。
- 如审查发现的缺陷涉及其他技能领域（安全、性能、数据），已建议转交并指明目标技能。
- 审查覆盖了差分行及其相邻上下文，不仅逐行阅读 diff。

## 审查模式与协作

**默认只读**：本技能默认不直接修改代码。审查者定位问题、给出分级建议和修复方向，但不执行修复。

**审查→修复→复核流程**：
1. **代码审查** 输出包含位置、证据、严重度、影响和修复建议的问题清单；
2. 如用户要求修复，主技能切换到 **Bug修复** 或 **功能实现**；
3. 修复完成后返回本技能，按原问题的位置、触发条件和影响逐项复核；修复方不得自行关闭审查问题。
4. 复核优先确认原问题及相邻回归风险，不无故扩大到与变更无关的全库审查；新发现的独立问题另行记录。

## 问题严重度

审查结论按以下等级标记：

| 严重度 | 含义 | 动作 |
|---|---|---|
| Blocker | 阻断合并或发布——数据丢失、安全暴露、行为错误、兼容中断 | 必须修复后方可交付 |
| High | 重要正确性、安全或数据风险，但对受影响面有限 | 在当前迭代中必须修复 |
| Medium | 明确缺陷、较大维护风险或违背已确认约定 | 应在本迭代或下一迭代修复 |
| Low | 非阻塞改进——可读性、命名、小范围重复 | 可在后续版本中优化 |
| Nit | 纯风格偏好差异，不影响正确性和可维护性 | 建议采纳，不视为缺陷 |

## 审查结论输出

审查结果必须包含以下可复核信息：

```
[严重度] 标题
文件/位置：
证据（行号、运行结果、静态分析引用）：
触发条件：
影响（行为/安全/性能/兼容/维护）：
修复建议：
置信度（高/中/低）：
需转交的技能（可选）：
```

## 路由与协作

可将专项工作转交给：功能实现、TDD开发、Bug修复、代码设计、安全审查与威胁建模。默认将上述技能作为专项协作方，当前主技能保留目标、进度和最终验收责任。只有当前技能已不再适合承担主目标时才切换主技能；切换或协作时提供上下文、已验证事实、未决问题、风险等级、期望输出和返回条件。协作结果返回当前主技能验收；没有新增证据或状态变化时不得重复转交。

## 状态模型

每项工作只能以以下状态之一汇报：已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证。状态后必须附证据或阻塞原因；“已完成”要求验收条件已经被验证，“无法验证”必须说明所缺环境、权限或数据。

## 完成标准

- 范围、假设、事实和决策边界清楚。
- 高风险事项有处置、接受、转交或明确阻塞结论。
- 关键结论具备可复核证据，验证与回退方式匹配风险。
- 未决事项具有负责人、触发条件或下一步，不用模糊措辞掩盖不确定性。
- 每个审查意见都区分了 Blocker/重要/建议等级；无模糊的"建议改进"。
- 审查覆盖了差分行及其相邻上下文：调用方、被调用方和共享状态的变更已纳入检查。
