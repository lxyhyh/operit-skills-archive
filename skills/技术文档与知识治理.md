# 技术文档与知识治理

## 使命

维护准确、可发现、可追溯并随系统演进的技术知识体系。 本技能是纯指导型工作框架：Trae 应读取项目事实、现有约束和可用工具后自主选择分析方法、参数、工具与执行顺序，而不是机械套用固定命令。

## 适用情形

当任务涉及受众与任务、信息架构、事实来源、决策记录、变更同步、失效归档时启用。若请求主要属于其他专业技能，应说明边界并转交，不重复制造相互冲突的结论。

## 工作原则

- 文档即产品：文档与代码同等版本化；代码变更若没有同步文档更新视为不完整。
- 唯一真源：每类知识（架构、API、部署、决策）有且只有一个权威文档位置；禁止在 Issue/PR/Slack 中隐藏关键决策。
- 可发现优先于完整：文档必须可被搜索和导航到；组织结构比内容全面性更重要。
- 腐烂即债务：过时文档比无文档更危险；定期审计文档与代码的一致性，删除或标注过期内容。

## 工作流程

### 1. 审计当前知识分布

识别文档存放位置、格式、负责人和更新状态；找出缺失、过时和冲突的文档。

### 2. 设计信息架构

按受众（开发者/运维/产品）和内容类型（架构/API/运维/决策）设计目录结构和交叉引用规则。

### 3. 制定维护机制

确定文档模板、审查流程、更新触发条件（代码变更/发布/决策）和过期检测方式。

### 4. 执行内容同步

修复发现的缺失和冲突，将散落知识迁移到架构中的权威位置。

### 5. 建立文档质量门禁

PR 检查中纳入文档变更要求；定期运行文档-代码一致性扫描。
## 用户确认边界

遇到关键需求歧义、不可逆或破坏性操作、生产环境写入、敏感权限或秘密、外部发布、费用承诺、法律与业务风险取舍时，必须暂停并请求用户或责任人明确确认。普通的只读检查、可逆分析和已授权范围内的实现由 Trae 自主推进，避免对每个细节反复询问。

## 专项边界

不虚构系统行为、命令结果或决策；不让文档替代可执行验证和代码事实。

## 路由与协作

可将专项工作转交给：对话转PRD、计划转Issue、领域建模、API设计与契约治理、知识库管理。默认将上述技能作为专项协作方，当前主技能保留目标、进度和最终验收责任。只有当前技能已不再适合承担主目标时才切换主技能；切换或协作时提供上下文、已验证事实、未决问题、风险等级、期望输出和返回条件。协作结果返回当前主技能验收；没有新增证据或状态变化时不得重复转交。

## 状态模型

每项工作只能以以下状态之一汇报：已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证。状态后必须附证据或阻塞原因；“已完成”要求验收条件已经被验证，“无法验证”必须说明所缺环境、权限或数据。

## 完成标准

- 范围、假设、事实和决策边界清楚。
- 高风险事项有处置、接受、转交或明确阻塞结论。
- 关键结论具备可复核证据，验证与回退方式匹配风险。
- 未决事项具有负责人、触发条件或下一步，不用模糊措辞掩盖不确定性。
- 每份关键文档都有最后验证日期，超过约定时限的已标注为待审查。
- 文档的目录/索引/搜索路径已经过验证，不依赖个人记忆查找。
