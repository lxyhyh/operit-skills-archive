# 领域建模

## 建模闭环

### 输入与范围
输入业务目标、用例、现有术语、代码模型和外部系统约束。先确定限界上下文，再讨论实体、值对象、聚合、领域服务和事件；不要把数据库表或 UI 表单直接当作领域模型。

### 冲突与压力测试
对同义异名、同名异义和职责跨上下文的问题建立术语冲突表。使用并发修改、重复请求、状态回退、权限变化、部分失败和历史数据等场景压力测试不变量。多个合理模型并存时记录适用条件和权衡，由业务规则而非个人偏好裁决。

### 交付与完成标准
输出上下文边界、统一语言、核心对象与不变量、关键领域事件、上下文关系、代码偏差和待决策项；同步 `CONTEXT.md`，仅为难撤销且存在真实权衡的决策创建 ADR。完成要求术语可映射到用例，关键不变量经边界场景验证，未决冲突有负责人或下一步。


主动构建和打磨项目的领域模型。这是_主动的_纪律 — 挑战术语、创造边界场景、在术语和决策刚结晶时就写下来。

## 文件结构

大多数仓库有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
```

如果 `CONTEXT-MAP.md` 存在，则表示有多个上下文。

延迟创建文件 — 只有确实有东西要写时才创建。

## 会话期间的行为

### 对照词汇表挑战术语
当用户使用与 CONTEXT.md 中现有语言冲突的术语时，立即指出。

### 打磨模糊语言
当用户使用模糊或过载的术语时，提出精确的标准术语。

### 讨论具体场景
当讨论领域关系时，用具体场景压力测试。创造探测边界的场景。

### 交叉引用代码
当用户说明某事如何工作时，检查代码是否一致。发现矛盾时指出来。

### 内联更新 CONTEXT.md
术语解决后立即更新 CONTEXT.md，不要批量做。

### 谨慎提供 ADR
仅当以下三条都满足时才提供 ADR：
1. **难撤销** — 后续改变主意成本高
2. **没有上下文会令人困惑** — 未来读者会疑问"为什么这样做？"
3. **真实权衡的结果** — 有真正的替代方案，你因特定原因选择了其中一个
