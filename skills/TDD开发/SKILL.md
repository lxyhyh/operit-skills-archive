# TDD开发

## 核心理念

**核心原则**：测试应通过公共接口验证行为，而非实现细节。代码可以完全重写，测试不应受牵连。

**好测试**是集成风格的：通过公共 API 执行真实代码路径。它们描述系统**做什么**，而非**怎么做**。好测试在重构后依然存活。

**坏测试**与实现耦合：mock 内部协作对象、测试私有方法。信号：重命名内部函数后测试失败，但行为没变。

**循环论证测试**：在断言里重复实现逻辑 — `expect(add(a, b)).toBe(a + b)` — 测试永远不可能与代码不一致。期望值必须来自独立的真实来源：已知正确的字面量、手算例子、规格说明。

## 反模式：水平切片

**不要**先写所有测试再写所有实现。这是"水平切片"。

水平切片产生**垃圾测试**：测试的是_想象的_行为而非_实际的_行为。

**正确做法**：垂直切片（tracer bullet）。一个测试 → 一个实现 → 重复。

```
错误（水平）：
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
```

## 工作流

### 1. 规划
- [ ] 从规格和代码确认外部行为及接口影响；公开接口取舍不明确时请用户决定
- [ ] Trae 根据风险和验收标准确定行为测试优先级
- [ ] 列出要测试的行为（非实现步骤）
- [ ] 若测试行为会改变已确认的公开契约、产品语义、兼容性承诺或任务范围，则先请求用户确认；否则在已授权范围内直接进入第一个红—绿循环

### 2. Tracer Bullet
写一个测试确认系统的一个方面：
```
RED:   写第一个行为的测试 → 测试失败
GREEN: 写最少代码通过 → 测试通过
```

### 3. 增量循环
对每个剩余行为重复：RED → GREEN。每次只写一个测试，只写刚好通过当前测试的代码。

### 4. 重构
所有测试通过后：
- [ ] 提取重复代码
- [ ] 加深模块（把复杂逻辑放到简单接口后面）
- [ ] 应用 SOLID 原则
- [ ] 思考新代码暴露了什么
- [ ] 每次重构后运行测试

**红的时候绝不重构。** 先变绿。

## 输入与不适用场景
- 输入：已确认的验收标准（来自 PRD/Issue）、可观察行为描述、测试框架和项目约定。
- 不适用：验收标准模糊且无法从代码推断、测试环境不可用、需求仍在剧烈变化、纯探索性原型。

## 状态与协作
- 每轮状态：红（测试失败且符合预期）→ 绿（最小实现通过）→ 重构（行为不变）。
- 每个切片完成：对应验收行为通过、必要重构完成，且测试在约定环境中稳定复现；是否要求代码审查由项目门禁和任务风险决定。
- 代码审查发现的行为缺陷可进入新的红—绿循环；纯风格建议不应伪装成验收标准。
- 协作期间当前主技能保留切片状态与最终验收责任；专项结果返回当前循环复核。

## 每轮清单

- [ ] 测试描述行为而非实现
- [ ] 测试只使用公共接口
- [ ] 测试能在内部重构后存活
- [ ] 期望值是独立字面量，非重算代码
- [ ] 代码对这个测试来说是最简的
- [ ] 没有添加猜测性的功能
