# Bug修复

## 输入与分流
优先获取或自行查找：可复现症状、失败命令/测试、完整错误与日志、相关代码和配置、环境、最近变更、根因判断及证据。能从项目获得的信息先查后问。

- 根因已证实或高概率且有明确验证方式：进入修复。
- 根因不明、难复现、跨组件或性能回归：携带现有证据转 **调试诊断**。
- Android 构建系统异常：按情况转 **APK编译问题诊断**。

## 修复流程
1. 复核根因能否解释症状，区分事实、假设和已排除项。
2. 确定最小可交付修复范围及外部可观察行为；优先变更小、易验证、易回滚的方案。
3. 在合适 seam 建立或保留失败信号。若不适合自动化测试，记录可重复的验证步骤和限制。
4. 实施最小充分修改。具体文件、工具、顺序与实现由 Trae 根据代码库决定，避免顺手重构无关区域。
5. 重跑原失败路径，并根据风险选择相关测试、类型检查、静态检查、构建或冒烟验证。
6. 审查兼容性、安全、错误处理、边界输入和无关差异。

## 用户确认边界
授权范围内的局部可逆修复由 Trae 自主推进。公开 API/持久化结构/权限模型变化、大范围重写或删除、生产操作、费用、发布、提交或推送前，说明影响和回退方式并等待确认。

## 输出
报告症状与根因、证据等级、实际修改、原问题验证、相关回归验证、未验证项、风险与回退方式。状态使用"已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证"。

## 完成标准与返回
- "已完成"要求原问题已修复且原复现步骤不再触发，相关回归测试通过。
- 如修复由代码审查或调试诊断触发，修复完成后必须返回源技能进行复核。
- 如修复由自动编译触发（编译错误修复），必须返回自动编译重跑原构建验证。
- 仅修改代码但未在原触发上下文中验证不算完成。状态使用“已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证”。
