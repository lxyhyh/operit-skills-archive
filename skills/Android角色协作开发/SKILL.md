# Android角色协作开发
## 概述
**多角色 + 质量门禁 + 接口契约** 的团队协作框架。业务需求来自用户；Trae 根据当前任务自主选择最小充分角色集合和协作粒度，不为形式固定角色数量。首次使用时先复用已有项目事实，仅对会改变产品方向的缺失决策询问用户。

## 触发条件
用户含 `@角色` / `角色调度` / `多角色协作` / `multi agent` 或具体角色命令时激活。

## 工作流程
### Phase 1：检测
只读查找 `dev_roles.json`：不存在则提出 Phase 2 配置计划，存在则进入 Phase 3 复用。读取失败时报告路径、错误与回退方案，不把默认值静默写入项目。

### Phase 2：首次生成角色
#### 2.1 需求收集
**先查后问**：从现有代码、规格和对话提取应用目标、核心功能与技术栈。只有缺失信息会改变业务范围、用户体验或关键架构取舍时才询问；普通技术选择由 Trae 给出依据后自主决定。

#### 2.2 10 个角色能力槽位
角色表是可选能力目录，不代表每个任务都要依次激活全部角色。

| # | 角色 | 标识符 | 核心职责 |
|---|------|--------|----------|
| 1 | 产品与需求 | `pm` | 需求澄清、用户故事、验收标准；不得自行编造业务需求 |
| 2 | Android 架构 | `architect` | 模块设计、技术选型、依赖边界、接口契约 |
| 3 | Android UI/UX | `ui` | Material Design 3、Compose/XML 交互、无障碍与适配 |
| 4 | 客户端界面 | `frontend` | Compose/XML、状态呈现、导航、动画与 UDF |
| 5 | 数据与集成 | `backend` | Room/DataStore、网络客户端、Repository、同步与离线策略 |
| 6 | 构建工程 | `build` | Gradle、签名、混淆、变体、APK/AAB |
| 7 | 测试工程 | `test` | 单元/UI/集成测试、边界场景与回归证据 |
| 8 | 交付与运维 | `devops` | CI/CD、多环境、发布、监控与回滚协调 |
| 9 | 安全与隐私 | `security` | 权限、敏感数据、供应链、隐私与网络安全审计 |
| 10 | 性能工程 | `perf` | 启动、渲染、内存、电量与基准测试 |

#### 2.3 配置格式与确认门
每角色可包含 `display_name`, `avatar_emoji`, `responsibility`, `system_prompt`, `trigger_keywords`, `deliverables`, `quality_gate`。首次创建、重置或更新 `dev_roles.json` 前，必须展示目标路径、完整字段计划、覆盖影响和回退方式，并等待用户确认；确认后再写入。

### Phase 3：复用
读取并校验 `dev_roles.json`，按当前目标和证据选择通常 1–3 个必要角色，注入对应约束并记录任务历史。配置与项目事实冲突时先报告差异，不静默覆盖。

### Phase 4：任务分发
**按当前任务激活最小充分角色集合。独立工作可并行，有依赖的工作按接口契约推进；只有真实用户决策边界或已约定的写入确认门才暂停。**
1. **确定主角色**：每阶段只有一个主角色，对阶段目标和验收负责。
2. **最小输出**：交付最基础可验证的产出，不过度设计。
3. **按边界推进**：授权范围内自主推进；遇到业务取舍、不可逆操作或权限扩张时再请用户决定。
4. **按证据扩展**：用户提出新需求，或新证据表明现有能力不足时，可以增加角色；说明原因、期望产出和返回条件。
5. **上下文传递**：角色交接包含目标、证据、产出、未决问题、风险和返回条件。
6. **冲突仲裁**：技术冲突先按证据、约束和可逆性裁决；涉及业务方向或不可逆取舍时交由用户决定。

## 质量门禁
门禁应按任务风险和已确认目标裁剪；不相关项标记“不适用”并说明理由。未满足适用门禁时不得宣称该角色任务完成，但可报告部分完成或阻塞。

| 角色 | 门禁 |
|------|------|
| 产品与需求 | 需求来源可追溯、验收可测试、优先级有依据；需要业务裁决的内容已确认或明确待决策 |
| Android 架构 | 跨模块契约已记录；循环依赖已消除或有获批迁移方案；关键决策按需附 ADR |
| Android UI/UX | 关键交互取舍已确认；相关 Token、深色模式、尺寸与无障碍状态有验证或明确缺口 |
| 客户端界面 | 关键 UI 状态可验证；字符串/颜色遵循项目资源策略；复用程度与任务规模相称 |
| 数据与集成 | 数据访问和错误路径有验证；同步、离线或迁移策略按任务需要记录 |
| 构建工程 | 目标变体可复现；签名和敏感配置处理正确；仅验证任务涉及的变体 |
| 测试工程 | 达到约定覆盖目标；关键边界有测试；已知不稳定测试已修复、隔离或记录风险与负责人 |
| 交付与运维 | 目标流水线可执行；密钥安全；与发布风险相称的回滚方案可用 |
| 安全与隐私 | 相关危险权限、敏感数据和混淆规则已审查；未决风险有等级与处置建议 |
| 性能工程 | 指标达到约定目标或差距已量化；检测到的相关泄漏已修复，或有复现证据、风险与后续计划 |

## 技能联动
专项技能作为协作方，不自动抢占主任务；结果必须返回主角色验收。

| 角色 | 主技能 | 可选协作技能 |
|------|---------|-------------|
| 产品与需求 | 产品分析与实验治理 | 对话转PRD、需求追问文档 |
| Android 架构 | 代码设计 | 领域建模、API设计与契约治理、数据库设计与数据迁移 |
| Android UI/UX | 无障碍与国际化 | 产品分析与实验治理、技术文档与知识治理 |
| 客户端界面 | 功能实现 | TDD开发、代码审查、性能分析与优化 |
| 数据与集成 | 功能实现 | API设计与契约治理、数据库设计与数据迁移 |
| 构建工程 | 自动编译 | Android开发环境搭建、APK编译问题诊断、CI-CD与发布管理 |
| 测试工程 | 测试策略与质量保障 | TDD开发、调试诊断、Bug修复 |
| 交付与运维 | CI-CD与发布管理 | 线上可观测性与事故响应、备份恢复与灾难恢复 |
| 安全与隐私 | 安全审查与威胁建模 | 身份认证与权限设计、隐私合规与数据治理、依赖升级与技术债治理 |
| 性能工程 | 性能分析与优化 | 线上可观测性与事故响应、调试诊断 |

## 接口契约
使用 `Provider → Consumer：Input → Output` 表达依赖。主角色确保跨模块契约明确，实施角色依契约实现，测试角色依契约验证。

## 命令速查
`@pm`/`@产品` → 产品与需求；`@architect`/`@架构师` → Android 架构；`@ui`/`@设计师` → Android UI/UX；`@frontend`/`@前端` → 客户端界面；`@backend`/`@后端` → 数据与集成；`@build`/`@构建` → 构建工程；`@test`/`@测试` → 测试工程；`@devops`/`@运维` → 交付与运维；`@security`/`@安全` → 安全与隐私；`@perf`/`@性能` → 性能工程；`@all`/`@全员` → 全员评审；`@roles reset` → 提出重置计划；`@roles update <角色>` → 提出更新计划；`@gate <角色>` → 查看门禁状态。

配置文件：`<项目根目录>/dev_roles.json`。未明确项目目录时先建议候选路径，不直接在默认目录写入。

## 状态与证据模型
共享任务状态使用：`进行中 / 部分完成 / 已阻塞 / 需用户决策 / 已完成 / 已转交`。角色阶段或领域结果另行记录，不替代共享状态。
- `已完成`要求约定范围内的适用门禁通过，或例外已获明确接受。
- 角色交接必须携带：当前任务目标、已完成产出、验证证据、未决问题、风险等级和返回条件。
- 每阶段只允许一个主角色；协作者不改变主角色分配。
- 同一状态无新增证据时不得重复调用同一角色。

## 反模式
- ❌ 简单局部任务也强制经过产品、架构等完整角色流水线
- ❌ AI 自行定义业务需求或替用户作不可逆取舍
- ❌ 一次性规划全部 10 角色流水线
- ❌ 一个角色越权包揽所有层
- ❌ 不输出必要交接信息
- ❌ UI 实现角色擅自改变已确认的数据契约
- ❌ 在不合适的层直接访问持久化实现
- ❌ 测试只覆盖 happy path
- ❌ 未说明缺口就强行通过适用质量门禁
- ❌ 越过接口契约直接依赖下游实现
