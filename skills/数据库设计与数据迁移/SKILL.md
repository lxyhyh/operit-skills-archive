# 数据库设计与数据迁移

## 使命

建立符合业务不变量的数据模型，并安全演进结构和数据。 本技能是纯指导型工作框架：Trae 应读取项目事实、现有约束和可用工具后自主选择分析方法、参数、工具与执行顺序，而不是机械套用固定命令。

## 适用情形

当任务涉及实体关系、约束索引、事务一致性、容量访问、兼容迁移、校验回滚时启用。若请求主要属于其他专业技能，应说明边界并转交，不重复制造相互冲突的结论。

## 工作原则

- 模型反映业务不变性：表结构、约束和关系必须源自业务规则，不是 ORM 便利性或前端表单的镜像。
- 迁移应优先支持安全回退：提供对应的回滚脚本或经过验证的备份恢复路径；不可逆迁移（如删除列）必须明确标注、提供备份恢复方案并获取额外审批。
- 迁移在生产数据副本上验证：不在开发库上测试迁移就推向生产等于猜测；使用脱敏的生产数据副本进行迁移验证。
- 锁与性能：迁移必须评估在目标数据量下的锁持有时间和对在线服务的影响；大表变更采用在线 DDL 或分批策略。

## 工作流程

### 1. 分析当前数据模型与业务需求

审查现有 schema、约束、索引和实际数据分布，识别与业务规则的偏差。

### 2. 设计目标模型与迁移路径

定义目标 schema；为每个变更编写正向迁移和回滚脚本；标注不可逆迁移并说明理由。

### 3. 在副本上验证迁移

使用与生产等量级的脱敏数据执行迁移，测量耗时、锁影响和数据完整性。

### 4. 执行迁移

按计划窗口执行迁移；监控锁等待、复制延迟和错误率；异常时立即执行回滚。

### 5. 验证与清理

迁移完成后验证数据完整性、约束有效性、索引使用和性能基线。
## 用户确认边界

遇到关键需求歧义、不可逆或破坏性操作、生产环境写入、敏感权限或秘密、外部发布、费用承诺、法律与业务风险取舍时，必须暂停并请求用户或责任人明确确认。普通的只读检查、可逆分析和已授权范围内的实现由 Trae 自主推进，避免对每个细节反复询问。

## 专项边界

不在无备份和验证时执行破坏性迁移；不可逆操作、停机窗口和数据丢失风险必须确认。

## 领域深化

### 迁移模式

选择迁移策略的决策分支：
- **在线 DDL**（MySQL InnoDB ALGORITHM=INPLACE / PostgreSQL CONCURRENTLY）：允许并发读写，适合大表，但耗时更长且需额外磁盘空间；部分操作不支持。
- **影子表**（新建表 + 数据回填 + 原子重命名）：适合复杂重构且在线 DDL 不支持的操作，回滚简单（保留旧表），但存在短暂写丢失窗口。
- **蓝绿部署**：完整副本环境切换，零停机、快速回切，但需要双倍资源且协调复杂度高。
- **停机窗口迁移**：在计划维护窗口内执行，最可控但影响可用性，仅当其他方法不可行且有明确 RTO 时使用。

选择依据：表大小、读写负载、允许的锁定时间、数据库引擎能力、回滚 RTO。

### 回滚保障

每次迁移必须定义：
- **回滚条件**：什么触发回滚（校验失败、性能退化、错误率上升、超时）。
- **回滚步骤**：具体 SQL 或命令序列，不能仅靠"逆向操作"口头保证。
- **回滚验证**：回滚后如何确认数据完整性和服务正常。
- **回滚时间预估**：与 RTO 对比，超限则必须有降级方案。

### 索引原则

- **覆盖索引**：WHERE + SELECT + ORDER 全部在索引内时避免回表，但索引体积和写入开销随之增加。
- **选择性优先**：高基数列先于低位数列，联合索引最左前缀规则决定可用性。
- **避免过度索引**：每增加一个索引都增加写入延迟；定期审计未使用索引并移除。
- **部分索引 / 条件索引**：仅索引查询频繁的子集（如 `WHERE status = 'active'`），减小体积。
- **锁与并发**：PostgreSQL CREATE INDEX CONCURRENTLY 不阻塞写入但需要额外扫描；MySQL Online DDL 对某些操作仍会获取元数据锁。

### 事务边界

- **事务应尽可能短**：长事务持有锁、阻塞清理、导致复制延迟；将业务逻辑放在事务外。
- **幂等写入**：使用 INSERT ... ON CONFLICT / UPSERT 或业务幂等键防止重试重复。
- **批量操作分批**：每次 1000-10000 行，避免锁升、日志爆炸和长时间阻塞。
- **隔离级别匹配风险**：读已提交适合大多数场景；可重复读 / 串行化仅在有明确写偏、幻读或因果一致性需求时使用。

### 常见反模式

- **无迁移脚本**：手动在生产数据库中执行 DDL 而无法重复执行、审计或回滚。
- **未测试迁移回滚**：只有正向迁移脚本而未在同样数据量的测试环境中执行回滚。
- **单一大事务迁移**：将整张表的所有变更包在一个事务中，锁死所有并发操作。
- **隐式类型转换**：迁移中修改列类型（如 INT→BIGINT, VARCHAR 长度变更），在旧驱动/ORM 下产生静默截断或类型错误。
- **缺失校验步骤**：迁移完成但未校验行数、校验和、外键完整性和应用正常读写。

### 领域门禁

在交付数据库设计或迁移方案前必须确认：
- 迁移方法已根据表大小和负载特性选择，并记录理由。
- 回滚步骤可执行且预估时间 ≤ RTO。
- 缺少任意索引不会导致功能错误（仅影响性能）；关键查询有覆盖索引分析。
- 迁移前后的数据校验步骤已定义（行数、校验和、抽样业务验证）。
- 迁移脚本已纳入版本控制，可在任意环境重现。

## 路由与协作

可将专项工作转交给：领域建模、API设计与契约治理、备份恢复与灾难恢复、性能分析与优化。默认将上述技能作为专项协作方，当前主技能保留目标、进度和最终验收责任。只有当前技能已不再适合承担主目标时才切换主技能；切换或协作时提供上下文、已验证事实、未决问题、风险等级、期望输出和返回条件。协作结果返回当前主技能验收；没有新增证据或状态变化时不得重复转交。

## 状态模型

每项工作只能以以下状态之一汇报：已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证。状态后必须附证据或阻塞原因；“已完成”要求验收条件已经被验证，“无法验证”必须说明所缺环境、权限或数据。

## 完成标准

- 范围、假设、事实和决策边界清楚。
- 高风险事项有处置、接受、转交或明确阻塞结论。
- 关键结论具备可复核证据，验证与回退方式匹配风险。
- 未决事项具有负责人、触发条件或下一步，不用模糊措辞掩盖不确定性。
- 每次迁移都有对应的回滚脚本且已在等量级数据上验证过。
- 不可逆迁移已获得明确授权，回退路径（如备份恢复）已文档化。
