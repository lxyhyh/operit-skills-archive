# Operit 技能创建器（Skill Creator）

## 角色定位

把用户的一句话需求转化为符合 Operit 平台规范的完整技能（Skill）。从零开始设计、生成 `SKILL.md` 及配套资源，写入 `/sdcard/Download/Operit/skills/` 并完成校验。

本技能**从零创作**：只凭用户对任务的描述与通用知识现场设计，不依赖用户的历史操作记录，也不要求用户先做过同类事情。

## Operit 技能的本质

- 一个技能 = 一个文件夹 + 必含 `SKILL.md`
- 系统优先读取 frontmatter 里的 `name` / `description` 来决定何时自动加载；若缺失，回退读取文件前 40 行里的 `name:` / `description:`
- 可选配套目录：`scripts/`、`templates/`、`examples/`、`assets/`，在 `SKILL.md` 里用相对路径引用
- 技能根目录固定：`/sdcard/Download/Operit/skills/<skill_name>/`
- 技能列表开关关闭后，文件仍在本地，但 AI 不会使用

## 必要输入

优先收集（信息不足时明确说“需要补充信息”，最多追问 1-3 个关键问题）：

1. 技能要解决什么任务（一句话能说清）
2. 触发场景 / 信号词：用户在什么情况下会用到它
3. 输入是什么、期望输出是什么
4. 是否依赖文件、脚本、API 或平台现有包/工具

## 工作流程

### 第 1 步：需求澄清

确认“做什么、给谁用、什么时候触发、输入输出是什么”。若用户已表达清楚，直接进入设计，不过度追问。

### 第 2 步：设计技能

- 命名：小写字母与短横线连接，如 `weekly-report-generator`；避免空格与特殊字符
- 检查重名：先查看 `/sdcard/Download/Operit/skills/` 下是否已有同名目录；有则提示用户改名或明确确认覆盖
- 规划结构：大多数技能一个 `SKILL.md` 就够；只有涉及固定模板、示例、脚本或平台规范时才加配套目录

### 第 3 步：编写 SKILL.md（核心）

frontmatter 必须写：

```markdown
---
name: <技能名，与目录名一致>
description: <一句话说明做什么 + 触发信号词，便于 AI 自动发现>
---
```

正文结构平台**不强制**，官方仅要求涵盖 4 块：适用场景、执行步骤、约束边界、期望输出。

**默认禁止套用 bug-fixer 那套五段式标题**（角色定位 / 必要输入 / 工作流程 / 输出格式 / 原则）。它是该技能的自定义写法，不是平台习惯；只有用户明确点名"要类似 bug-fixer 的简短风格"时才能用。按下面规则选结构：

- **默认（常规任务型）**：以官方四块为骨架，标题可贴合任务表述，但**不要**采用"角色定位/必要输入/工作流程/输出格式/原则"这套组合
- **多环节 / 流程型技能**：按阶段分章组织（准备 → 执行 → 校验 → 交接），参考 `SandboxPackage_DEV`
- **知识 / 审查 / 判定型技能**：适用范围 → 判定标准 → 作答规范 → 边界
- 若用户指定了结构或风格，按其要求执行
- **生成后自检**：若产物的章节标题恰好是"角色定位、必要输入、工作流程、输出格式、原则"这五个，说明仍被五段式锚定，必须按任务类型改写结构与标题

每块内容标准：步骤具体到可执行动作、边界一句话说清、期望输出给出明确格式（模板见 `templates/skill-template.md`）。

### 第 4 步：生成配套资源（按需）

- `templates/`：技能需要固定文案/文件结构时放模板
- `examples/`：放 1 个完整示例，帮助执行者理解期望结果
- `references/`：技能依赖平台规范或外部文档时放参考，避免正文臃肿
- `scripts/`：需要确定性执行（文件操作、数据处理等）时放脚本

### 第 5 步：写入磁盘

- 创建 `/sdcard/Download/Operit/skills/<skill_name>/`
- 写入 `SKILL.md` 及配套文件
- **必须**：写入前向用户说明将要创建/修改的内容与路径，得到确认后再执行

### 第 6 步：校验并交接

- `SKILL.md` 存在且位于技能根目录
- frontmatter 含 `name` / `description`，且 `name` 与目录名一致
- 步骤可执行、无歧义、不依赖未知资源
- 无重名冲突
- 向用户汇报：技能路径、结构、内容摘要，并询问是否需要开启软件中的技能列表开关

## 改进与优化（可选模式）

用户要求“改进/优化/测试技能”时：

1. 先读取现有 `SKILL.md` 与配套目录
2. 针对用户反馈的问题定位修改点，保持原有风格一致
3. 修改前向用户说明改动内容，确认后写入
4. 完成后说明改了哪里、为什么改、如何验证

## 原则

- 从零创作：根据需求描述与通用知识生成，不依赖用户历史操作记录
- 一个技能只解决一类任务，不要做成大杂烩
- `description` 必须包含触发信号词，否则 AI 可能不会自动发现它
- 步骤要具体到可执行动作，禁止空话套话
- 创建/修改任何文件前必须经用户确认
- 不确定平台规范时，查阅本技能目录下 `references/operit-skill-spec.md`
