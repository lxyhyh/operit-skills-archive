# Issue分类

在项目 Issue 跟踪器上对 Issue 和外部 PR 进行一致、可审计的分流。标签名称应先读取项目现有约定，不假定所有项目都使用同一套状态。

## 输入要求
- Issue/PR 链接或正文、评论、作者、时间及已有标签。
- 项目现有标签、状态机和贡献约定；PR 还需要 diff、检查结果和关联 Issue。

## 推荐状态模型
若项目没有既定规范，可建议：类别 `bug` / `enhancement`；状态 `needs-triage` / `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`。不得未经确认创建、删除或重命名标签。

## 分类流程
1. 收集正文、评论、标签、作者和时间；PR 同时读取 diff、检查结果和关联 Issue。
2. 区分已验证事实、合理推断和未证实声明。对 bug 尽量复现，对 PR 验证其是否解决声明的问题。
3. 校验类别、严重度、优先级和状态是否与证据一致，输出推荐值、理由、置信度和缺失信息。
4. 信息不足且会改变分类时使用 **追问引擎**；术语或边界冲突时协作使用 **领域建模**。
5. 为可执行任务形成 brief：背景、期望行为、复现或验收步骤、约束和相关文件。
6. 展示拟变更后等待用户确认，再执行平台写操作并复核结果。

## 异常与交付
- 无法判断时使用“需用户决策”，列出所缺信息；不以低置信度结论覆盖现有分类。
- 建议与项目标签体系冲突时优先采用项目约定，并记录偏差。
- 输出分类建议、证据与置信度、关联工件、实际平台变更和失败项。
- 状态使用“已完成 / 部分完成 / 需用户决策 / 已阻塞”；“已完成”要求约定的分类操作已应用并可审计。

## AI 内容标识
遵循仓库现有贡献规范。若平台或项目要求标明 AI 生成内容，使用其规定格式；没有规定时，先向维护者建议简短且语言一致的标识，不写死特定英文模板。

## 用户确认门
读取和分析可自主进行。以下写操作必须先展示拟变更并等待用户明确确认：发布或编辑评论、修改标签或负责人、关闭或重开 Issue、批准、关闭或合并 PR。批量操作还应列出对象清单和回退办法。
