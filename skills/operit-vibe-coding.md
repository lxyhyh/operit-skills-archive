# operit-vibe-coding

## 适用范围

从零开始在 Operit 平台上用 vibe coding（AI 驱动的迭代开发）把"一句话应用想法"变成**结构清晰、可维护、可迭代**的完整应用工程（代码 + 文档 + 测试 + 验证记录）。

触发信号词：帮我开发 / 做一个应用、从零开始做XX、vibe coding 开发、迭代式开发一个项目、做一个可以长期维护的XX。

不适用（应转交）：已有代码的编译/构建 → **自动编译**；模块化诊断 → **模块化分析**；缺陷修复 → **Bug修复**；测试策略规划 → **测试策略与质量保障**。

## 执行流程

vibe coding 的核心不是一次性生成全部代码，而是**小步快跑、每步可验证、全程保持可维护性**。按六个阶段推进，每阶段有完成标准。

### 阶段 0：需求澄清与范围界定

1. 确认核心功能、平台形态（Android / Web / 脚本 / Sandbox / 本地服务）、技术偏好、交付形态
2. 输出一句话需求 + MVP 范围 + 验收标准（怎样算"跑通了"）
3. 向用户复述并**确认后再开工**；信息不足只追问 1-3 个关键问题

**完成标准**：MVP 范围与验收标准已与用户确认。

### 阶段 1：工程脚手架（可维护性的地基）

1. 建立标准项目结构（按 `templates/project-structure.md` 骨架）
2. 初始化版本控制（git init + .gitignore + 首次提交，环境可用时）
3. 创建 README.md 骨架（项目名、一句话简介、运行方式、目录说明）

**完成标准**：目录骨架与版本控制就位，README 已有内容。

### 阶段 2：架构先行（先画地图再走路）

1. 写简短架构说明 `docs/ARCHITECTURE.md`：模块职责、数据流、模块间接口边界
2. 明确 MVP 核心路径（最小功能闭环）
3. 模块单一职责、低耦合、配置与常量与代码分离；不过度设计但预留扩展点

**完成标准**：核心路径与模块边界已明确并记录。

### 阶段 3：迭代式 vibe coding 开发（每轮一个可验证增量）

每轮固定节奏：

1. 明确本轮目标与验收标准
2. 涉及接口/边界先更新架构约定，再写实现代码
3. 编写实现，小步提交，遵循命名与代码规范
4. 立即运行验证本轮目标
5. 用 `templates/iteration-log.md` 记录本轮内容
6. 更新 README / CHANGELOG，提交信息用 Conventional Commits（`feat:` / `fix:` / `docs:` 等）
7. 回到第 1 步，直到 MVP 完整闭环

**完成标准**：每轮增量可运行、可验证，MVP 完整闭环。

### 阶段 4：测试与验证

1. 关键业务逻辑写自动化测试，用平台运行器（code_runner / 脚本能力）执行
2. 每轮完成时跑主流程冒烟测试
3. 在目标环境（设备 / 沙盒 / 浏览器）实测，**不只是"能编译"**
4. 记录通过 / 失败原因 / 修复记录到 iteration-log

**完成标准**：自动化测试 + 冒烟 + 实测均通过并保留证据。

### 阶段 5：文档与维护基线（交付前必做）

1. README 补全：运行方法、架构简述、目录说明、依赖清单
2. 注释只解释"为什么"与业务边界，不重复代码本身
3. CHANGELOG 汇总全部变更
4. 遗留 TODO / 已知问题归档到 `docs/TODO.md`，不隐藏
5. 按 `references/maintainability-checks.md` 自检

**完成标准**：文档与实现一致，自检项全部通过。

### 阶段 6：交接与后续迭代

1. 汇报项目结构、运行方式、已验证内容、如何继续迭代
2. 明确下一步可做的迭代项（来自 TODO / 用户新需求）
3. 新需求从阶段 0 / 3 继续循环，保持既有结构与规范

**完成标准**：用户清楚如何运行、如何继续迭代。

## 校验与交付

每次阶段交接与最终交付，做以下核验：

- 目录结构符合工程模板，模块职责单一，根目录无散落文件
- 命名自解释，配置与常量已分离，每条依赖有引入理由
- 关键逻辑有自动化测试，主流程已实测通过（不只编译通过）
- README 与实际运行方式一致，CHANGELOG 覆盖全部变更
- 提交记录小步、可回溯；遗留 TODO 已归档未隐藏
- 汇报格式：**项目结构 → 运行方式 → 已验证内容 → 已知问题/TODO → 下一步迭代建议**

## 边界

- **增量优先**：禁止一次性生成全部代码再"碰运气"；每轮迭代必须可运行、可验证
- **可验证产物**：不产出无法运行、无法检查的文件；每个产物给出验证方法
- **可维护性优先**：模块单一职责、命名清晰、常量/配置分离、依赖引入说明理由
- **架构变更需确认**：改动已确认的模块边界/接口前，先说明理由并征得用户同意
- **不破坏已有文件**：涉及用户既有代码/配置先备份，删除范围须经用户确认
- **技术栈务实**：优先平台与环境已有能力，不为炫技引入陌生技术
- **文档同步**：代码变了文档必须同步更新，文档与实现不一致即视为缺陷

## 期望输出

完整应用工程（含文档、测试、验证记录）：

```
项目根目录/
├── README.md        # 简介 + 运行方式 + 目录说明
├── CHANGELOG.md     # 变更记录
├── src/             # 应用源码
├── tests/           # 自动化测试
├── docs/            # ARCHITECTURE.md / TODO.md
├── scripts/         # 构建/运行/辅助脚本
└── iteration-log.md # 迭代过程记录
```

汇报格式：项目结构 → 运行方式 → 已验证内容 → 已知问题/TODO → 下一步迭代建议。
