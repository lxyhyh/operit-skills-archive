# 代码设计

## 执行流程
1. 分析当前模块的接口大小、行为深度和 seam 位置
2. 识别符合"小接口大行为"原则的重构机会
3. 设计方案：将复杂实现移到接口背后，通过接口测试验证行为
4. 实施重构并确保已有测试通过
5. 输出设计决策记录：原问题、新设计、权衡和迁移路径

## 异常处理
- 重构可能引起破坏性变更时优先提供兼容过渡方案
- 现有测试覆盖不足时先补充行为测试再重构

## 交付产物
- 重构后的代码变更（接口定义 + 实现）
- 设计决策记录（为什么这样设计、什么替代方案被排除）
- 测试结果（表明外部行为未改变）

## 状态模型
每项工作汇报状态：已完成 / 部分完成 / 已阻塞。
"已完成"要求重构已实施且所有测试通过。

设计**深模块**：小接口背后有大量行为，放置在干净的 seam 处，通过该接口可测试。

## 词汇表（使用精确词汇）

**模块** — 任何拥有接口和实现的东西。可以是一个函数、类、包或跨层切片。

**接口** — 调用者正确使用模块需要知道的一切：类型签名 + 不变量、顺序约束、错误模式、所需配置、性能特性。

**实现** — 模块内部的东西，其代码体。

**深度** — 接口提供的杠杆：调用者每学一个单位的接口能触发的行为量。**深模块** = 小接口 + 大实现；**浅模块** = 大接口 + 小实现。

**Seam（接缝）** — 可以在不编辑原位置的情况下改变行为的地方；模块接口所在的_位置_。

**适配器** — 在 seam 处满足接口的具体实现。

**杠杆** — 调用者从深度中获得的收益：更多能力/更少学习。

**局部性** — 维护者从深度中获得的收益：变更、bug、知识、验证集中在一个地方。

## 原则

- **深度是接口的属性，不是实现的属性。**
- **删除测试**：想象删除这个模块。如果复杂度消失，它是透传；如果复杂度在 N 个调用者中重新出现，它物有所值。
- **接口即测试面**：调用者和测试穿过同一个 seam。
- **一个适配器 = 假设的 seam。两个适配器 = 真实的 seam。**

## 可测试性设计

1. **接受依赖，不创建依赖**
2. **返回结果，不产生副作用**
3. **小表面面积** — 更少方法 = 更少测试
