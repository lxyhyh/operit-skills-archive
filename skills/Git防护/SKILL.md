# Git防护

目标是在执行高风险 Git 操作前提供可靠、可回退的保护，而不是假设某个特定 AI 客户端或固定脚本环境。

## 评估
- 识别需要保护的操作：推送、强制推送、硬重置、清理未跟踪文件、删除分支、改写历史等。

## 输入要求
- 仓库路径或远程仓库 URL
- 已有分支保护规则和 CI/CD 策略（若存在）
- 团队对危险操作的定义（可推断：push --force, reset --hard, clean -fd, branch -D, rebase --onto 等）

## 执行流程
1. 只读分析仓库现有 hooks、远端保护设置和团队工作流
2. 列出需拦截的操作清单及其风险等级
3. 设计方案：远端保护优先 + 本地 hook 补充，给出具体配置和验证方式
4. 展示方案并等待用户确认后实施
5. 验证每种危险操作均被正确拦截或要求显式确认

## 异常处理
- 如果项目已有 pre-commit 等 hook 框架，必须兼容而非覆盖
- 如果远端已配置保护规则，本地不重复拦截（避免双重确认）
- 安装失败时回滚所有变更，恢复到配置前状态

## 交付产物
- 实际安装的 hook 文件和配置变更记录
- 验证结果：每个被拦截/允许的操作都有对应测试通过记录
- 绕过方式和回退步骤的文档

## 状态模型
每项工作汇报状态：已完成 / 部分完成 / 已阻塞 / 需用户决策。
"已完成"要求所有目标危险操作均已验证被拦截；"部分完成"必须列出哪些操作未覆盖及原因。



## 方案要求
Trae 自主选择兼容当前环境的 hook 管理方式，并确保：
- 默认拒绝或要求显式确认危险参数；
- 不拦截安全的只读操作；
- 安装、卸载和临时绕过方式清晰；
- 脚本可移植、可审查，失败时采取安全默认值；
- 提供针对允许/拒绝场景的验证。

## 用户确认门
写入 hooks、修改 `core.hooksPath`、安装依赖或调整仓库/全局 Git 配置前，先展示文件、作用域、影响和回退步骤并等待确认。不得擅自执行 push、force push、reset、clean 或历史改写。
