# 对话转PRD

## 综合与交付协议

### 输入与事实等级
仅综合当前对话及其明确引用的工件。区分“已确认需求”“从事实推导的约束”“待确认事项”；不得为了文档完整而补造用户、指标、时间、预算或技术决策。

### PRD 生成流程
1. 提取背景、目标、非目标、用户与场景。
2. 将需求转为可观察的行为和验收标准，覆盖关键失败与边界场景。
3. 记录依赖、非功能要求、风险、开放问题和决策人。
4. 检查术语与 `CONTEXT.md`、ADR 及现有产品行为是否冲突。
5. 发布到 Issue 跟踪器或写入文件前展示目标位置与完整内容并等待确认。

### 交付状态
输出 PRD、待确认事项和建议交给 `计划转Issue` 的切片入口。状态使用“草案 / 需用户决策 / 已确认 / 已发布”；“已发布”必须附目标位置或 URL，不把生成草案称为发布完成。

## 下游交接与返回
只有状态为“已确认”的 PRD 才进入 `计划转Issue`；每个 Issue 应回链到 PRD 条目和验收标准。`TDD开发` 或 `功能实现` 完成后，由任务主技能按 PRD 逐条验收。实现发现需求矛盾或验收不可行时返回本技能修订草案并重新确认，不在实现阶段静默改写需求。


将当前对话上下文和代码库理解综合成 PRD。**不要追问用户** — 只综合已知信息。

## 流程

1. **探索代码库**（如果尚未）理解当前状态
2. **勾画测试 seam** — 优先使用现有 seam，提议新的 seam 时选尽量高的位置。最理想是一个 seam。
3. **写 PRD** 并使用以下模板，然后发布到 issue 跟踪器，打上 `ready-for-agent` 标签

## PRD 模板

### 问题陈述
用户面临的问题，从用户视角出发。

### 解决方案
从用户视角出发的解决方案。

### 用户故事
编号列表。格式："作为 \<角色\>，我想要 \<功能\>，以便 \<收益\>"

### 实现决策
- 将构建/修改的模块
- 这些模块的接口
- 技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

**不**包含具体文件路径或代码片段（例外：原型产生的片断比文字更精确时，可以内联附注）。

### 测试决策
- 好测试的定义
- 哪些模块将被测试
- 测试的先例

### 非范围

### 进一步备注

## 用户确认门
发布到 Issue 跟踪器、覆盖现有规格或修改项目状态前，先展示最终 PRD 和目标位置并等待用户确认；仅在对话中生成草稿不需要额外确认。
