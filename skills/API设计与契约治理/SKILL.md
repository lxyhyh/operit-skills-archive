# API设计与契约治理

## 使命

设计稳定、清晰、可演进且可验证的服务契约与兼容策略。 本技能是纯指导型工作框架：Trae 应读取项目事实、现有约束和可用工具后自主选择分析方法、参数、工具与执行顺序，而不是机械套用固定命令。

## 适用情形

当任务涉及资源与动作、输入输出、错误语义、幂等分页、版本兼容、契约测试时启用。若请求主要属于其他专业技能，应说明边界并转交，不重复制造相互冲突的结论。

## 工作原则

- 契约即产品：API 修改必须遵守兼容策略（新增可选字段=兼容，删除/重命名/改变必需字段=不兼容），版本化所有不兼容变更。
- 契约先于实现：先定义接口、数据格式和错误语义，再编码；契约变更必须同步更新文档、测试和依赖方通知。
- 契约测试是最重要的兼容性证据之一：基于契约的消费者驱动测试、流量观测和变更分析共同构成兼容性验证。
- 最小暴露原则：只暴露调用方真正需要的字段和端点；内部实现细节不得泄露到契约。

## 工作流程

### 1. 盘点现有契约

扫描当前 API 定义、版本、调用方和兼容性承诺，识别隐式契约（未文档化但被依赖的行为）。

### 2. 分析变更影响

对每个提议变更评估兼容性影响：新增/修改/删除字段或端点，错误响应变化，认证要求变化，速率限制变化。

### 3. 设计或修订契约

按兼容策略设计目标契约，包括端点、请求/响应模型、错误格式、认证模式、速率限制和弃用计划。

### 4. 验证契约正确性

生成/运行契约测试，覆盖正常路径、边界值、错误路径、向后兼容性；对破坏性变更要求所有已知调用方的迁移计划。

### 5. 交付契约制品

输出 OpenAPI/GraphQL schema、变更日志、迁移指南、弃用时间线和调用方通知清单。
## 用户确认边界

遇到关键需求歧义、不可逆或破坏性操作、生产环境写入、敏感权限或秘密、外部发布、费用承诺、法律与业务风险取舍时，必须暂停并请求用户或责任人明确确认。普通的只读检查、可逆分析和已授权范围内的实现由 Trae 自主推进，避免对每个细节反复询问。

## 专项边界

不强制绑定 REST、RPC 或 GraphQL；不在缺乏迁移方案时破坏已发布契约。

## 领域深化

### API 版本策略

选择版本指示方式的决策分支：
- **URL 路径版本**（`/v1/`, `/v2/`）：最显式，适合公共 API 和重大不兼容变更，但产生路由重复和维护成本。
- **请求头版本**（`Accept: application/vnd.api+json;version=2`）：保持 URL 清洁，适合内容协商场景，但缓存分层和调试较复杂。
- **查询参数版本**（`?version=2`）：实现简单，但容易被忽略、不适合强制版本控制。
- **无版本 / 仅演化**：仅在绝对保证向后兼容且消费者完全受控时适用——通常是内部服务。

选择依据：消费者多样性、兼容承诺强度、缓存基础设施、API 网关能力。

### 字段演化规则

| 变更类型 | 向后兼容 | 安全操作 | 需版本升级 |
|----------|----------|----------|------------|
| 新增可选请求字段 | ✅ | 是 | 否 |
| 新增必填请求字段 | ❌ | 否 | 是 |
| 新增响应字段 | ✅ | 是 | 否 |
| 删除响应字段 | ❌ | 否 | 是（先标记废弃 ≥1 版本） |
| 重命名字段 | ❌ | 否 | 是 |
| 放宽校验（如长度限制增大） | ✅ | 是 | 否 |
| 收紧校验 | ❌ | 否 | 是 |
| 新增枚举值（响应中） | ✅ | 是 | 否 |
| 新增枚举值（请求中） | ❌ | 否 | 是 |
| 变更字段语义（保持同名） | ❌ | 否 | 必须新字段名 |

### 兼容性矩阵

评估变更影响时检查：
- **语法兼容**：旧客户端能否成功解析新响应（无未知字段崩溃、类型不变）。
- **语义兼容**：旧客户端拿到新响应后的行为是否仍正确（非仅不崩溃）。
- **协议级兼容**：HTTP 状态码、错误格式、幂等键、分页游标、重试行为是否一致。

### 常见反模式

- **透传内部数据模型**：直接将 ORM 实体序列化为 API 响应，泄漏内部结构并绑架接口演化。
- **巨型端点**：单端点返回所有关联资源，导致不可控的数据量、缓存失效和耦合。
- **混合关注点**：认证、授权、业务逻辑、数据聚合、格式转换混在同一端点，难以独立演进。
- **缺失幂等键设计**：写操作无幂等键或使用自然键不稳定，导致重试时重复副作用。
- **静默 Breaking Change**：变更语义但不改字段名/类型，消费者无感知但行为错误。
- **分页信息不一致**：不同端点的分页格式、游标语义、总数字段命名不统一。

### 领域门禁

在交付 API 设计结论前必须确认：
- 指定了版本策略并说明理由（含演进触发条件）。
- 对每个修改字段执行了兼容性检查并记录结果。
- 高风险变更提供了迁移窗口和废弃时间线。
- 契约测试覆盖了正常路径、边界值和至少一个兼容验证场景。
- 错误响应格式与 HTTP 状态码语义一致。

## 路由与协作

可将专项工作转交给：领域建模、身份认证与权限设计、数据库设计与数据迁移、技术文档与知识治理。默认将上述技能作为专项协作方，当前主技能保留目标、进度和最终验收责任。只有当前技能已不再适合承担主目标时才切换主技能；切换或协作时提供上下文、已验证事实、未决问题、风险等级、期望输出和返回条件。协作结果返回当前主技能验收；没有新增证据或状态变化时不得重复转交。

## 状态模型

每项工作只能以以下状态之一汇报：已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证。状态后必须附证据或阻塞原因；“已完成”要求验收条件已经被验证，“无法验证”必须说明所缺环境、权限或数据。

## 完成标准

- 范围、假设、事实和决策边界清楚。
- 高风险事项有处置、接受、转交或明确阻塞结论。
- 关键结论具备可复核证据，验证与回退方式匹配风险。
- 未决事项具有负责人、触发条件或下一步，不用模糊措辞掩盖不确定性。
- 契约变更已标注兼容性等级，破坏性变更已提供迁移路径和弃用时间线。
- 所有已知调用方已纳入影响分析；无文档化调用的接口通过使用数据确认后方可移除。
