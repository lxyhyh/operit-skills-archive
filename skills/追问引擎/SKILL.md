# 追问引擎

## 输入与职责边界
- 输入：计划、设计草案或模糊需求描述；可自行查证的信息（代码库、文档、配置）不得作为提问内容。
- 职责：逐层追问直到关键决策分支明确。不负责维护项目文档（CONTEXT.md/ADR），不负责综合 PRD。
- 当需要持续沉淀术语、上下文和架构决策时，切换到需求追问文档。

## 目标
把模糊计划收敛为可执行决策，而不是追求问题数量。先利用对话、代码库、现有文档和工具消除可自行查证的不确定性，再询问只有用户能够决定的事项。

## 提问策略
1. 建立决策树，区分已知事实、可查事实、合理默认值和用户决策。
2. 默认每轮聚焦一个主要决策点，给出背景、推荐选项及影响。
3. 若多个问题彼此独立、答案简短且合并能减少往返，可作为一个清晰编号的问题组提出；不要把相互依赖的问题堆在同一轮。
4. 用户已明确授权或行业惯例足以支持可逆选择时，由 Trae 说明假设后自主推进。
5. 新答案改变前提时，更新决策树，不机械沿用旧问题清单。

## 不应追问
- 能从代码、配置、文档、日志或工具结果直接获得的事实；
- 不影响外部行为、交付范围或风险边界的实现细节；
- 用户已经回答、明确授权，或可安全回退的局部选择。

## 需要用户决定
业务目标与优先级、公开承诺、不可逆或破坏性操作、权限/费用扩张，以及存在明显权衡且无法从现有约束推出的架构选择。

## 停止条件与输出
当剩余不确定性不会改变当前可交付方案，或已明确标记为后续决策时停止追问。输出：目标与非目标、已确认决策、Trae 自主采用的假设、待用户决策、验收标准、风险与下一技能建议。状态使用“已完成 / 部分完成 / 需用户决策 / 已阻塞”。
