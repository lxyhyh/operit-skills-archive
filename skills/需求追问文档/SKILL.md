# 需求追问文档
## 输入、停止条件与交付
### 输入
读取需求或设计草案、代码库事实、已有 `CONTEXT.md`、ADR 和项目约束。可自行从仓库查证的信息不得反复询问用户；只追问会改变范围、架构、风险或验收的决策。

### 停止条件
满足以下条件后停止追问：目标与非目标清楚；关键术语已统一；正常、边界和失败场景已有结论，或被明确记录为待决策；不可逆决策及替代方案已记录；验收标准可观察。无法当场决定的事项必须记录负责人、触发/截止条件或默认方案，不以无限追问阻塞推进。

### 异常与交付
需求与代码事实冲突时并列呈现证据并请求裁决；用户暂不能决定时记录为待决策，不擅自补造。输出更新后的 `CONTEXT.md`、必要的 ADR、决策日志、未决事项及建议下一技能。

共享任务状态使用“进行中 / 部分完成 / 需用户决策 / 已阻塞 / 已完成”；追问结果另记为“决策树已闭合 / 带受控未决项退出”。带受控未决项退出时，共享状态不得标为已完成，除非约定交付物本身就是一份可执行的未决事项清单。

## 核心流程
1. **启动追问会话**：运行 **追问引擎** 技能，对用户的计划或设计逐层追问。
2. **调用领域建模**：在追问过程中按需调用 **领域建模** 技能。
   - 发现模糊术语时澄清并写入 `CONTEXT.md`。
   - 遇到难撤销的决策时创建 ADR。
3. **产生工件**：
   - `CONTEXT.md` — 项目的共享领域语言与边界；
   - `docs/adr/` — 架构决策记录；
   - 未决事项清单 — 负责人、触发/截止条件、默认方案和影响。
4. **完成标准**：影响当前范围、架构、风险或验收的分支均已有结论，或已作为受控未决项记录；术语已定义；关键决策可追溯；下一执行方能够识别哪些内容可推进、哪些必须等待。

## 写入确认门
创建或修改 `CONTEXT.md`、ADR 等项目文件前，先展示文件计划和关键变更并等待用户确认；仅做只读追问与草案输出时无需写入。

## 使用场景
- 开始实现新功能前做需求对齐；
- 复杂设计需要多方确认时；
- 建立项目统一领域语言时。
