# 合并冲突
## 输入要求
- 当前 Git 状态、当前分支、目标分支及正在进行的 merge/rebase/cherry-pick 类型。
- 冲突文件列表和操作目标；可用时读取关联 commit、PR、Issue 和设计记录。

## 单一解决流程
1. 只读检查 `git status`、提交图和冲突块，保存当前可恢复点；不先修改文件或改变 Git 状态。
2. 逐文件还原双方原始意图，区分可合并行为、互斥决策、生成文件和删除/重命名冲突。
3. 输出逐文件方案：双方意图、拟保留行为、权衡、风险及验证方式。存在业务或架构取舍时等待用户决定。
4. 用户确认后编辑冲突文件；生成文件优先通过可信生成流程重建，不手工拼接产物。
5. 运行与风险匹配的格式化、静态检查、类型检查和测试。失败时分析解决内容，不虚报完成，也不自动丢弃已完成工作。
6. 展示解决后的状态和验证证据，再请求是否暂存以及是否执行 `merge --continue`、`rebase --continue` 或 `cherry-pick --continue`。这些操作可能创建提交，必须单独获批。

## 中止、提交与推送边界
- `merge --abort` / `rebase --abort` / `cherry-pick --abort` 不是默认动作；当继续可能扩大损失或用户决定放弃时，说明会丢失的工作和可恢复方式后等待确认。
- 不自动创建额外提交，不自动修改提交消息，不自动推送。经用户批准执行 `--continue` 时，应明确它可能按 Git 流程创建或重写提交。
- 不发明双方均不存在的新行为；确需新行为时转为独立设计决策，而不是隐藏在冲突解决中。

## 交付与二层状态
输出逐文件解决记录、验证结果、当前 Git 状态、已暂存/未暂存文件、可能产生的提交和剩余决策。
- 共享任务状态：`进行中 / 部分完成 / 需用户决策 / 已阻塞 / 已完成`。
- Git 流程阶段：`已分析 / 冲突文件处理中 / 冲突文件已解决待继续 / continue 后复验 / 流程已结束`。
- 验证结果：`通过 / 失败 / 无法验证`。

映射规则：仅完成分析时共享状态为进行中或需用户决策；部分文件解决时为部分完成；所有冲突文件解决但尚未获批或执行 `--continue` 时为需用户决策，领域阶段为“冲突文件已解决待继续”；只有 Git 冲突流程已结束且约定验证通过时，才能标记共享状态“已完成”。

## 协作返回
若调用测试、构建、代码审查或 Bug 修复技能，合并冲突仍保留主任务的 Git 状态和最终验收责任；协作方返回验证证据，不自动执行暂存、continue、提交或推送。
