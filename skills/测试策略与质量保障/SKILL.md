# 测试策略与质量保障

## 使命

建立与项目风险匹配的分层测试策略、质量门槛和可追溯结论。 本技能是纯指导型工作框架：Trae 应读取项目事实、现有约束和可用工具后自主选择分析方法、参数、工具与执行顺序，而不是机械套用固定命令。

## 适用情形

当任务涉及需求风险、测试分层、覆盖缺口、环境与数据、质量门槛、发布证据时启用。若请求主要属于其他专业技能，应说明边界并转交，不重复制造相互冲突的结论。

## 工作原则

- 测试分层匹配风险：单元测试验证逻辑正确性，集成测试验证边界交互，E2E 测试验证关键用户旅程；不能所有风险都用单一测试层覆盖。
- 测试代码也是产品代码：测试的可读性、可维护性和运行速度与生产代码同等重要；flaky test 视同生产 bug 处理。
- 质量门禁自动化：测试、覆盖率、静态分析和安全扫描必须集成到 CI；通过门禁方可合并和发布。
- 测试设计先于实现：在编写代码前明确可观测行为和验收标准；测试描述行为（做什么）而非实现（怎么做）。

## 工作流程

### 1. 评估当前质量现状

分析现有测试分布（单元/集成/E2E）、覆盖率缺口、flaky test 频率和 bug 逃逸率。

### 2. 制定测试策略

按模块风险和变更频率确定每层的覆盖目标和具体技术栈；定义质量门禁指标。

### 3. 补充关键测试

从高频变更和高风险路径开始编写测试，优先补齐安全边界和异常路径的覆盖。

### 4. 建立 CI 质量门禁

配置测试自动运行、覆盖率报告、flaky test 检测和失败阻断规则。

### 5. 持续度量与改进

追踪 bug 逃逸率、测试运行耗时、flaky test 比例和覆盖率趋势，周期性调整策略。
## 用户确认边界

遇到关键需求歧义、不可逆或破坏性操作、生产环境写入、敏感权限或秘密、外部发布、费用承诺、法律与业务风险取舍时，必须暂停并请求用户或责任人明确确认。普通的只读检查、可逆分析和已授权范围内的实现由 Trae 自主推进，避免对每个细节反复询问。

## 专项边界

不替代功能实现或逐缺陷修复；不以覆盖率数字替代风险判断。

## 路由与协作

可将专项工作转交给：TDD开发、Bug修复、调试诊断、CI-CD与发布管理。默认将上述技能作为专项协作方，当前主技能保留目标、进度和最终验收责任。只有当前技能已不再适合承担主目标时才切换主技能；切换或协作时提供上下文、已验证事实、未决问题、风险等级、期望输出和返回条件。协作结果返回当前主技能验收；没有新增证据或状态变化时不得重复转交。

## 状态模型

每项工作只能以以下状态之一汇报：已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证。状态后必须附证据或阻塞原因；“已完成”要求验收条件已经被验证，“无法验证”必须说明所缺环境、权限或数据。

## 完成标准

- 范围、假设、事实和决策边界清楚。
- 高风险事项有处置、接受、转交或明确阻塞结论。
- 关键结论具备可复核证据，验证与回退方式匹配风险。
- 未决事项具有负责人、触发条件或下一步，不用模糊措辞掩盖不确定性。
- 质量门禁指标已量化并集成到 CI，包括具体阈值和豁免流程。
- flaky test 有独立跟踪清单和修复时效要求，不得通过反复重试掩盖。
