# 计划转Issue

## 切片与发布协议

### 输入与切片规则
读取已确认的 PRD/规格、验收标准、依赖和项目标签约定。按可独立演示和验证的纵向行为切片，不按前端/后端/数据库层横向拆分；基础设施任务必须说明它解锁的首个用户行为。

### Issue 质量门禁
每个 Issue 包含背景、用户可观察结果、范围与非目标、验收步骤、约束、依赖、风险和可并行性。依赖形成环时重新切片；验收必须依赖未来未完成工作时，标注为阻塞而非假装独立。

### 发布与异常
批量创建或修改前展示 Issue 清单、目标项目、标签、里程碑和依赖图并等待确认。平台不可访问时输出可导入的离线清单；部分创建失败时记录成功对象与失败原因，避免重复创建。状态使用“草案 / 需用户确认 / 部分发布 / 已发布 / 已阻塞”。

### 实现入口与验收返回
每个 Issue 指明推荐的实现入口：行为清晰且适合测试先行时可用 `TDD开发`；其他已确认需求可用 `功能实现`，二者不是必须串行。实现完成后按 Issue 验收步骤复核并回写证据；发现规格缺口时返回 PRD/规格责任方，不在 Issue 中私自改变产品语义。


通过垂直切片（tracer bullet）将计划拆分为可独立执行的 Issue。

## 流程

### 1. 收集上下文
从对话上下文中已有内容出发。如果用户传了 Issue 引用，从跟踪器中获取全文和评论。

### 2. 探索代码库（可选）
寻找预重构机会。"让变更容易，然后做容易的变更。"

### 3. 起草垂直切片
每个 Issue 是一个薄的垂直切片，贯穿所有集成层端到端，**不是**一个水平的单层切片。

**规则：**
- 每个切片提供一条窄但完整的路径经过每一层（schema, API, UI, 测试）
- 完成的切片可独立演示或验证
- 任何预重构应首先完成

### 4. 询问用户
展示推荐的分解方案（编号列表），每个显示标题/被谁阻塞/涵盖的用户故事。问：
- 粒度合适吗？
- 依赖关系正确吗？
- 需要合并或拆分吗？

### 5. 发布 Issue
按依赖顺序发布（阻塞者优先），使用 Issue 模板。

## 用户确认门
创建或批量修改 Issue、里程碑、标签和依赖关系前，先展示拆分结果及目标项目并等待用户确认。
