# 复用优先

## 适用范围

在 vibe coding 开发过程中，**写任何新代码之前**执行"现成方案优先"检查，避免重复实现已有的能力：

- 新功能要自己写之前：先查有没有平台包、项目已有依赖、成熟第三方库、设计规范组件可复用
- 引入新依赖前：先评估与现有依赖/平台能力是否重复
- 用户说"别自己写 / 用现成的 / 不要重复造轮子 / 有没有现成方案"时立即执行

不适用（应转交）：已有依赖的升级管理 → **依赖升级与技术债治理**；模块边界与接口评估 → **模块化分析**；对现成方案的代码审查 → **代码审查**。

## 判定标准

### "现成可用"的定义

满足以下**全部**条件才算可用，缺一不可：

1. **真实存在**：平台包、项目依赖、第三方库中确实有对应能力（查证过，不是凭印象）
2. **可验证**：能在当前项目环境中编译 / 运行 / 调用通过（不只看文档说支持）
3. **适配需求**：功能覆盖当前需求，或通过少量配置/扩展可达
4. **风险可接受**：许可证允许、无已知严重安全或维护问题

### 检查顺序（固定，按此序）

1. **平台能力**：Operit 已激活包与平台工具（如 various_search、file_converter、ffmpeg、code_runner、system_tools、extended_file_tools 等）——零依赖成本，最高优先
2. **项目现有依赖**：build 文件 / lockfile / 已有公共模块与工具类——不新增依赖成本
3. **生态成熟库**：该语言/框架的主流方案（查证 GitHub 维护状态、star 量级、发布频率、许可证）
4. **设计规范与组件库**：项目已定的 DESIGN-SPEC / 组件库（如 Miuix）中已覆盖的组件直接映射使用

### 允许自造的条件（需同时满足）

- 按上述顺序检查过**全部四层**且均无满足项；或
- 现成方案无法满足硬性需求（性能、许可、安全、定制深度），且已记录对比；或
- 引入依赖的成本（体积、维护负担、许可风险）高于自造，且已记录对比
- 用户明确要求自造（按用户要求，但仍应提示存在的现成方案）

**自造时必须记录**：评估过哪些现成方案、为何放弃、自造方案的范围。写在代码注释与 `templates/复用决策记录模板.md`。

## 执行流程

写新代码 / 新功能前，按以下步骤执行（可与编码同步进行，结论记录在案）：

1. **识别需求能力点**：把新功能拆成能力点（网络、文件、UI、数据解析、加密、图片处理、定时任务…），逐点检查
2. **查平台能力**：确认 Operit 已激活包中是否有对应工具；有则直接用 `package_proxy` 调用，不自己实现
3. **查项目依赖**：检查 build 文件、lockfile、已有公共代码；有则复用并引用，不重复实现
4. **查生态库**：对该能力点搜索主流方案，核对维护状态与许可证；选择后说明选择理由
5. **查规范与组件**：对照项目 DESIGN-SPEC / 组件库（如 Miuix），优先映射现成组件与令牌
6. **决策并记录**：采用现成方案 → 直接引用；确需自造 → 按"允许自造的条件"记录决策
7. **交付时自检**：按 `references/reuse-checklist.md` 逐项核对，自造项须有决策记录

## 边界

- **不为了"用库"而用库**：引入新依赖必须说明理由（体积、许可证、维护状态），防止依赖膨胀
- **现成 ≠ 可用**：文档说支持不算，必须在当前环境验证通过
- **安全与敏感场景**：加密、认证、密钥管理等**强制**使用成熟库，不自造（自造加密是重大红线）
- **不盲目追新**：选择维护活跃、兼容性好的稳定版本，而非最新版本
- **用户明确要求自造**时尊重用户决定，但仍提示存在的现成方案
- **决策要留痕**：复用或自造的结论记录在迭代日志 / 决策记录中，便于审查回溯
- **不重复造轮子 ≠ 否定一切实现**：业务逻辑、领域代码本来就该自己写；本技能约束的是"通用能力"的重复实现

## 期望输出

每次开发交付时附带**复用检查结论**：

1. 新功能涉及的能力点清单
2. 每个能力点的检查结果：平台包 / 项目依赖 / 生态库 / 规范组件 四层各查过什么
3. 采用方案：现成（引用哪个）或自造（决策记录：评估过什么、为何放弃、范围）
4. 自检结果：`references/reuse-checklist.md` 全部通过

汇报格式：能力点 → 检查过程（四层）→ 采用方案与理由 → 自检结论。
