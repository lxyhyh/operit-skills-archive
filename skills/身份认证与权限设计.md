# 身份认证与权限设计

## 使命

设计可靠的身份建立、会话管理、授权决策和权限审计模型。 本技能是纯指导型工作框架：Trae 应读取项目事实、现有约束和可用工具后自主选择分析方法、参数、工具与执行顺序，而不是机械套用固定命令。

## 适用情形

当任务涉及身份生命周期、认证因子、会话与令牌、角色属性策略、最小权限、审计与恢复时启用。若请求主要属于其他专业技能，应说明边界并转交，不重复制造相互冲突的结论。

## 工作原则

- 身份先于授权：必须先可靠地建立"是谁"（认证），才能决定"能做什么"（授权）；弱认证之上没有安全的授权。
- 最小权限：每个身份（用户/服务/设备）仅拥有完成当前任务所需的最小权限；默认拒绝，显式授权。
- 会话安全等同凭证安全：会话令牌的生成、存储、传输和失效必须采用与主凭证相同的安全标准。
- 权限决策可审计：每次授权决策必须可追溯到策略依据；权限变更必须有审批记录和时间线。

## 工作流程

### 1. 建模身份与角色

识别用户类型、服务账户和设备的身份模型；定义角色和权限的层次和继承关系。

### 2. 设计认证流程

选择认证方式（密码/SSO/MFA/生物识别），设计注册、登录、会话管理和注销流程。

### 3. 设计授权模型

定义权限粒度（RBAC/ABAC/ReBAC），设计策略决策点和策略执行点。

### 4. 实施安全控制

实现密码哈希、Token 管理、会话超时、失败锁定、异常检测和审计日志。

### 5. 验证与渗透测试

测试越权（横向/纵向）、会话固定、Token 重放、时序攻击等常见攻击模式。
## 用户确认边界

遇到关键需求歧义、不可逆或破坏性操作、生产环境写入、敏感权限或秘密、外部发布、费用承诺、法律与业务风险取舍时，必须暂停并请求用户或责任人明确确认。普通的只读检查、可逆分析和已授权范围内的实现由 Trae 自主推进，避免对每个细节反复询问。

## 专项边界

不存储真实秘密，不默认信任客户端，不将认证成功等同于拥有资源权限。

## 领域深化

### 认证协议决策树

| 场景 | 推荐协议 | 注意事项 |
|------|---------|---------|
| 服务端渲染 Web 应用（同域） | Session Cookie + HttpOnly + SameSite=Strict | 需 CSRF 保护；移动端不适用 |
| SPA + 自有 API | Authorization Code + PKCE (OAuth 2.1) | 避免 implicit flow；刷新令牌仅存后端或安全存储 |
| 移动原生应用 | OAuth 2.0 with PKCE + 设备绑定 | 不使用 embedded webview 做登录页 |
| 服务间通信（零信任） | mTLS + 短期 JWT（服务账户） | 证书轮换自动化 + 撤销列表 |
| 第三方集成 / API 访问 | API Key + HMAC 签名或 OAuth 2.0 Client Credentials | Key 必须可独立撤销和轮换 |
| IoT / 受限设备 | 设备证书 + 预共享密钥，配合网关层长连接代理 | 离线场景回退策略需明确定义 |

### 令牌生命周期

- **访问令牌**：≤ 15 分钟，Opaque 或 JWT，不建议存储在前端 localStorage。
- **刷新令牌**：≤ 7 天，单次使用（每次刷新换新令牌），检测重放攻击（若同一刷新令牌被使用两次则撤销该用户/设备的所有刷新令牌）。
- **ID 令牌（OpenID Connect）**：仅用于身份信息传递，不用于授权。
- **令牌撤销**：必须支持单点撤销（单设备登出）和批量撤销（密码重置/账户锁定后废止全部会话）。

### 权限模型比较

| 模型 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| RBAC（角色-权限） | 组织层级清晰、岗位稳定 | 简单直观，审计清晰 | 角色爆炸——权限组合数 = 2^N |
| ABAC（属性-策略） | 细粒度、跨组织、动态属性 | 灵活精准、"为什么允许/拒绝"可解释 | 策略评估复杂，需策略引擎 |
| ReBAC（关系-权限） | 社交图、多租户、文件共享 | 自然表达"谁对什么有权限因为什么关系" | 关系解析需递归或专用查询引擎 |
| PBAC（策略合并） | 大型企业、合规多域 | 统一策略语言 + 可审计 | 实现门槛高、性能需仔细管理 |

选择原则：从 RBAC 起步，当角色 > 20 或出现属性交叉条件时引入 ABAC/ReBAC，不一次过设计。

### 安全反模式

- **密码哈希错误**：使用快速哈希（SHA-256）而非 bcrypt/scrypt/argon2。正确选择：argon2id（首选）> bcrypt（≥ 12 轮）> scrypt。
- **默认凭据 / 硬编码密钥**：代码仓库中含 API Key、数据库密码、JWT 签名密钥。
- **JWT 无有效期 / 无签名验证**：`exp` 缺失或极长，或接收端不验证 `alg`、签发者、受众。
- **顺序检查认证**：如先查数据库再比密码——正确做法是恒定时间比较哈希。
- **会话固定**：登录后不旋转会话 ID；logout 不清除服务端会话状态。
- **缺乏速率限制**：登录端点、OAuth Token 端点、MFA 验证端点无速率限制和告警。

### 领域门禁

在交付认证/权限方案前必须确认：
- 认证协议已匹配客户端类型并在决策树中定位。
- 令牌有效期、存储位置与撤销策略已定义且与威胁模型匹配。
- 权限模型选择理由已记录；若 RBAC 角色 > 20，已有向 ABAC/ReBAC 的演进计划。
- 密码存储使用 argon2id/bcrypt/scrypt，无硬编码密钥。
- 关键端点（登录、Token 刷新、MFA、密码重置）已定义速率限制策略。

## 路由与协作

可将专项工作转交给：安全审查与威胁建模、隐私合规与数据治理、API设计与契约治理、数据库设计与数据迁移。默认将上述技能作为专项协作方，当前主技能保留目标、进度和最终验收责任。只有当前技能已不再适合承担主目标时才切换主技能；切换或协作时提供上下文、已验证事实、未决问题、风险等级、期望输出和返回条件。协作结果返回当前主技能验收；没有新增证据或状态变化时不得重复转交。

## 状态模型

每项工作只能以以下状态之一汇报：已完成 / 部分完成 / 已阻塞 / 需用户决策 / 已转交 / 无法验证。状态后必须附证据或阻塞原因；“已完成”要求验收条件已经被验证，“无法验证”必须说明所缺环境、权限或数据。

## 完成标准

- 范围、假设、事实和决策边界清楚。
- 高风险事项有处置、接受、转交或明确阻塞结论。
- 关键结论具备可复核证据，验证与回退方式匹配风险。
- 未决事项具有负责人、触发条件或下一步，不用模糊措辞掩盖不确定性。
- 每个角色的最大权限范围已文档化，特权提升路径已标注并有限制。
- 认证和授权决策的审计日志已包含所需字段（主体、操作、资源、时间、结果）。
