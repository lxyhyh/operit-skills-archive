# 调试诊断

## 适用范围
用于根因不明确、难复现、跨组件或性能回归的问题。已有明确根因并可直接修复时使用 **Bug修复**；Android 构建异常优先 **APK编译问题诊断**。

## 1. 建立反馈循环
选择能触达真实症状的最小可重复信号，例如行为测试、HTTP/CLI 脚本、浏览器自动化、trace 回放、差异比较或受控测试桩。反馈循环应尽量快速、确定、可由 Trae 重复运行；若无法自动化，明确人工观察标准。

## 2. 复现与最小化
确认原始症状，再逐步移除无关输入、调用者、配置或步骤。每次缩减都保留失败信号。无法稳定复现时，先提高观测性并记录环境差异，不凭代码直觉宣布根因。

## 3. 假设台账
为每项假设记录：排名、证据状态、预测、验证实验、结果与下一步。证据状态统一为：**已证实 / 高概率 / 待验证 / 已排除 / 信息不足**。向用户展示假设仅在领域知识可能改变业务前提或实验风险时必要；普通技术排序由 Trae 自主完成。

## 4. 可解释实验
每次实验尽量改变一个可独立解释的因素。彼此独立、只读且不会竞争资源的检查可以并行；并行结果要分别归因。优先调试器、trace 和目标日志，避免无边界地记录全部信息。临时仪表应可识别、可移除。

## 5. 根因判定与转交
只有当证据能解释症状、预测实验结果，且反向修正使反馈循环恢复时，才标记“已证实”。根因明确后，把最小复现、证据、影响范围和建议验证交给 **Bug修复**，不在诊断阶段顺手扩大重构。

## 根因交付与回归
根因定位后转交 Bug修复 进行修复。修复完成后必须使用原最小复现进行回归验证——修复代码不能仅通过新测试，必须确认原复现步骤不再触发问题。根因证据（日志、core dump、profiling 数据）作为交付物的一部分提供给修复方。

## 停止条件
出现以下情况时停止当前循环：后续实验不再增加信息；需要破坏性操作、生产访问、费用或权限扩张；需要用户业务/架构取舍；环境不足导致无法验证。相应状态标记为“需用户决策 / 已阻塞 / 无法验证 / 已转交”。

## 清理与输出
移除临时日志和测试桩（删除前遵守用户确认边界），保留有价值的回归测试。输出复现方式、假设台账、根因等级、关键证据、已排除项、残余未知、转交摘要和完成状态。
