# 模块化分析

## 适用范围

对一个代码项目做**模块化程度诊断**并产出改进建议：

- 判断模块划分是否合理、哪里该拆 / 哪里该合并
- 定位耦合过重、循环依赖、接口膨胀、越权访问等结构问题
- 为是否立项重构提供有证据、分优先级、含成本收益的依据

触发信号词：评估下项目模块化 / 模块化怎么样 / 模块划分合理吗 / 哪些模块该拆该合并 / 代码耦合太重 / 分析下模块化程度。

不适用（应转交）：实施重构 → **架构改进**、**代码设计**；澄清领域边界 → **领域建模**；功能开发与测试 → 对应开发技能。

## 判定标准

模块化程度按 **8 个维度**评估，每个维度必须输出三层：**证据 → 判断 → 确定性**。

| # | 维度 | 检查要点 |
|---|---|---|
| 1 | 边界清晰度 | 单一职责、高内聚、有公开入口、无"上帝模块" |
| 2 | 耦合度 | 依赖走接口、共享可变全局状态、横向依赖密度、分层方向 |
| 3 | 循环依赖 | 直接环 A→B→A、间接长环 A→B→C→A |
| 4 | 接口质量 | 小接口大行为、隐式接口、公共 API 膨胀、内部实现泄露 |
| 5 | 可替换性/可测试性 | seam、DI、mock 难易、替换实现成本 |
| 6 | 变更影响半径 | 跨模块提交占比、"牵一发动全身"的模块 |
| 7 | 重复代码 | 复制粘贴、重复策略实现 |
| 8 | 越权访问 | 跨模块直调内部实现、绕过公开 API |

**确定性分级**：`事实`（证据充分）/ `推断`（有线索）/ `待验证假设`（证据不足）。无证据不得下确定性结论。

**改进建议分级**（两类分开，不混排）：

- **低风险快速改进**：改动小、可验证、建议先做
- **结构性重构**：跨模块、可能有破坏性，**必须用户决策后再实施**

每条建议固定含：问题 / 证据 / 方案 / 预期收益 / 影响范围与迁移成本 / 风险与不改的后果 / 推荐强度（强中弱）/ 优先级（P0/P1/P2）。参考 `references/modularity-checkpoints.md`。

## 作答规范

1. **界定范围**：项目路径、技术栈、模块边界定义方式（目录/包/命名空间/服务），确认本次分析目标（整体概览 / 单模块 / 两模块间关系）与输出形式
2. **只读采集证据**：模块边界与公开入口、依赖图（import / 构建配置）、规模与单文件异常值、接口暴露面、变更历史（`git log --name-only` 的跨模块提交占比）、测试 seam 与 mock 难度、重复代码、运行证据（日志/性能中的模块热点）。**只读不写，不修改任何文件**
3. **逐维度评估**：按 8 维度给"证据 / 判断 / 确定性"；证据不足的维度标注"待验证假设"
4. **生成建议清单**：区分低风险快速改进与结构性重构，各按 P0/P1/P2 排序
5. **输出评估报告**：默认在对话中输出；用户要求时可写入 Markdown（写项目目录外，不污染仓库）。固定结构按 `templates/模块化评估报告模板.md`：总体结论 → 分维度评估表 → 建议清单 → 证据索引 → 下一步

## 边界

- **只读分析**：不修改任何代码与配置；实施重构须经用户决策后转交 `架构改进` / `代码设计`
- **证据优先**：事实与判断分离；无证据不下确定性结论，宁可标注低确定度也不臆断
- **评估不变革**：报告与建议不自动触发重构；结构性变更前必须用户拍板
- **尊重既有边界**：按项目自身定义的模块边界评估，不套用先入为主的分割偏好
- **指标务实**：不以行数 / 文件数作为唯一标准，结合依赖、变更与运行证据综合判断
- **不制造噪音**：证据不足的维度明确标注待验证，不强行打分

## 期望输出

交付物（5 项）：
1. **总体结论**：模块化水平一句话判断 + 最值得做的 1-2 个机会
2. **分维度评估表**：8 维度 × 证据 / 判断 / 确定性
3. **建议清单**：按优先级排序，区分低风险快速改进与结构性重构
4. **证据索引**：关键文件、依赖命令、git 命令位置
5. **下一步**：建议转交哪个技能 + 需用户拍板的决策点
