# 快速原型
## 原型实验契约
**原型是一次性实验，用来回答一个问题，而不是提前实现产品。**

### 1. 定义问题与判据
每个原型只回答一个主要问题。开始前写明假设、观察方式、成功/失败判据、时间预算和不验证的范围；无法说明判据时先澄清，不直接堆砌功能。

### 2. 选择形式与隔离
选择最低成本的逻辑、接口或 UI 原型，只实现产生证据所需的路径。
- 逻辑/状态问题：优先使用最小可运行程序或测试夹具，枚举关键状态、事件、不变量和高风险边界，使用内存数据和固定样例。
- 信息架构、布局或交互问题：生成少量差异足够大的 UI 方案，围绕同一任务和数据展示关键状态，使用占位数据，不接生产后端。
- 显著标注“一次性、未加固、不可直接发布”，并与生产代码、真实凭据和生产数据隔离。
- 优先复用已有运行器；只实现回答问题所需的错误处理、测试和抽象。若成本接近正式实现，停止并重新评估验证方式。

### 3. 写入与风险确认门
若原型会写入正式代码区、引入或升级依赖、产生费用、访问真实数据或外部服务，先展示文件/操作计划、影响和清理方式并等待用户确认。在隔离临时目录内且不触及敏感数据的可逆实验，可按既有授权执行。

### 4. 观察与结论
记录“问题、假设、观察、结论、仍未知事项”。共享任务状态使用“进行中 / 部分完成 / 需用户决策 / 已阻塞 / 已完成”；领域结果另记为“假设获支持 / 假设被否定 / 证据不足”，不得用领域结果替代任务状态。

### 5. 交付与退出
输出原型位置、运行方法、观察记录、领域结果、局限和正式方案建议。将结论沉淀到 PRD/ADR 后，由用户决定删除、归档或继续隔离；删除或大范围迁移前必须确认。未经重新设计、测试和安全审查，不得把原型直接升级为生产实现。
